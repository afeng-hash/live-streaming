直播场景下的IM架构设计

客户端要先跟im集群中任意一台netty服务器进行长连接，长连接协议是tcp或者websocket都是可以的  
客户端把消息推送给 im服务器；im服务器内部会发送一个mq消息，mq消息是给到我们下游服务自定义业务处理  
当下游业务确定要把消息反向推给客户端的时候，他需要去检验一下用户是否在线；  
接收方在线的话，它通过mq投递给一个router服务，router这个服务实现主要基于 rpc 的调用，router可以任意调用 im服务的 rpc接口；具体要调用哪一台服务，这个得有客户端与im服务有一个连接关系，检索出来连接的是哪一台机器，然后通过rpc去请求到对应的那一台机器，那个机器再把消息反向推送给接收消息的客户端

心跳检测：
客户端在连接 im服务之后，会在本地调用方这边开启一个定时器，定时器会每隔一段时间发送一个心跳包消息体给到 im服务接入层  
im服务接收到心跳包之后，上报到 rpc 层，rpc层再把消息存到redis层里面，记录一下用户的心跳时间，来断定用户的网络情况和在线情况

发送消息的ack确认机制：
发送消息时im服务需要对消息的可达性进行一个确认

通常的做法是 im服务推送一条消息后，会等待客户端的一条ack确认

这里可以基于mq的延迟消息，当推送一条消息出去之后，延迟一条mq消息

mq延迟一段时间回来之后，再去判断ack标记是否有做一个清除

ack是存储在redis的一个map中进行一个记录
